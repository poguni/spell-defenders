# 맞춤법 수비대 단계별 개발 프롬프트

> 작성일: 2026-10-10 · 기준 문서: `docs/맞춤법 수비대 기획서.md` v0.4
> Claude Code에 복사해 붙여 넣어 쓰는 개발 단계별(M1~M8) 프롬프트 모음입니다.

---

## 사용 방법

1. **한 번에 한 단계만** 진행합니다(기획서 12.1). 단계마다 **새 대화**로 시작하고, 그 단계에 적힌 모델로 바꾼 뒤 프롬프트를 붙여 넣습니다.
2. 프롬프트는 모두 아래 **0장 공통 규칙**을 먼저 읽게 되어 있으므로 공통 규칙을 따로 붙여 넣을 필요는 없습니다.
3. 단계가 끝나면 Claude가 `docs/진행 기록.md`에 한 일과 남은 일을 적습니다. 쉬었다가 다시 시작할 때는 9장 **"이어서 하기"** 프롬프트를 씁니다.
4. 각 단계의 **"확인 기준"**은 선생님이 직접 확인합니다. 통과하면 다음 단계로 넘어갑니다.
5. 단계 프롬프트 안의 `기획서 n장`은 `docs/맞춤법 수비대 기획서.md`의 장 번호입니다.

## 0. 공통 규칙 (모든 단계에 적용)

Claude는 매 단계 시작 때 이 장을 읽고 따릅니다.

1. **범위 지키기**: 이번 단계에 적힌 일만 합니다. 다음 단계 기능을 미리 만들지 않습니다. 기획서에 없는 기능을 덧붙이지 않습니다.
2. **먼저 묻기**: 기획서에 정해지지 않은 부분이나 해석이 둘 이상인 부분은 코드를 쓰기 전에 질문합니다. 작업 시작 전에 "할 일 목록과 확인 방법"을 짧게 보여 줍니다.
3. **실행 가능한 상태로 끝내기**: 단계가 끝나면 `npm run dev`로 실행되고, `npm test`와 `npm run build`가 통과해야 합니다.
4. **진행 기록**: 단계 끝에 `docs/진행 기록.md`에 다음을 추가합니다. 날짜, 단계 이름, 한 일, 확인 결과(테스트 출력 요약), 남은 일·알려진 문제, 다음 단계에서 먼저 볼 파일.
5. **커밋**: 단계 끝에 git 커밋을 하나 만듭니다(메시지 예: `M1: 프로젝트 생성과 16:9 화면 틀`).
6. **문서 위치**: 새로 만드는 문서(md, html)는 모두 `docs/`에 둡니다.
7. **이모지 금지**: 화면, 코드, 문서 어디에도 이모지를 쓰지 않습니다. 그림이 없을 때는 단색 도형과 글자로 대신합니다.
8. **API 키 금지**: OpenRouter 키를 코드, `.env`, 저장소, 배포 설정 어디에도 넣지 않습니다(기획서 11장).
9. **정답 정확성 최우선**: `reviewed: false`인 문제는 학생에게 출제하지 않습니다. 맞춤법 판단이 애매하면 Claude가 정하지 말고 표시해서 선생님에게 넘깁니다.
10. **화면 기준**: 16:9 무대를 통째로 확대·축소합니다. 1920×1080, 1536×864, 1366×768에서 잘리지 않아야 합니다. 터치와 마우스를 모두 지원(Pointer 이벤트)하고 터치 영역은 48px 이상입니다(기획서 10.3).
11. **코드 스타일**: 단순하게 씁니다. 한 번만 쓰는 추상화, 쓰지 않는 설정 옵션을 만들지 않습니다. 화면 문구는 초등학생이 읽기 쉬운 한국어로 씁니다.

## M1. 프로젝트 생성과 16:9 화면 틀

**추천 모델**: Opus 5.5 Medium · **확인 기준**: 1920×1080·1366×768에서 수비전 화면이 잘리지 않음

```text
맞춤법 수비대 M1 단계를 시작하자.
먼저 docs/맞춤법 수비대 단계별 프롬프트.md의 0장 공통 규칙과
docs/맞춤법 수비대 기획서.md의 0장, 7장, 10장, 12장을 읽어 줘.

이번 단계 목표: 프로젝트를 만들고, 임시 그림으로 수비전 화면을 배치한다. 게임 동작은 아직 만들지 않는다.

할 일
1. 이 폴더(프로젝트 루트)에 React 18 + Vite + TypeScript 프로젝트를 만들고 git 저장소를 초기화한다.
   - Vitest를 설정하고 예시 테스트 하나가 통과하게 한다.
   - 기획서 10.2 폴더 구조대로 빈 폴더를 만든다(필요한 곳만 .gitkeep).
2. 16:9 무대(Stage) 컴포넌트
   - 내부 좌표는 1920×1080 기준으로 배치하고, 창 크기에 맞춰 비율을 유지한 채 통째로 확대·축소한다(남는 공간은 단색 여백).
   - 창 크기가 바뀌면 즉시 다시 맞춘다.
3. 시작 화면: 앱 제목(글자), "시작하기" 버튼, 전체 화면 버튼(Fullscreen API, 지원하지 않으면 숨김).
4. 수비전 화면(임시 그림)
   - 왼쪽에서 오른쪽으로 가는 길 3줄(레인), 오른쪽 끝 성문, 성 위 수비대원 자리
   - 레인마다 임시 몬스터 1마리(단색 원 + 짧은 문장 말풍선), 움직이지 않아도 된다
   - 위쪽 정보 막대: 성벽 체력, 마나(점수), 웨이브 표시, 속도 버튼(보통 / 느리게 / 일시정지) 자리
   - 아래쪽 문장 카드 자리: 문장 한 줄과 보기 버튼 3개(눌러도 아직 동작 없음)
   - 나중에 그림 파일(public/assets/…)로 바꿔 끼우기 쉽게, 임시 그림은 한 컴포넌트 안에 모은다
5. 글꼴은 Pretendard 웹폰트. 문장 카드 글자는 1366×768 화면에서 실제 24px 이상으로 보이게 한다.
6. 확인
   - Playwright로 1920×1080, 1536×864, 1366×768 세 크기의 스크린숏을 찍어 잘림이 없는지 확인하고, 스크린숏은 docs/screenshots/M1/에 저장한다.
   - npm test, npm run build 통과.

하지 않을 일: 몬스터 이동, 정답 판정, 저장, 실제 그림 적용.
끝나면 docs/진행 기록.md에 기록하고 커밋해 줘.
```

## M2. 정답 판정 로직과 문제 검증

**추천 모델**: Opus 5.5 Medium · **확인 기준**: 판정 테스트 통과, 샘플 문제 30개가 검증 스크립트 통과

```text
맞춤법 수비대 M2 단계를 시작하자.
docs/진행 기록.md, docs/맞춤법 수비대 단계별 프롬프트.md 0장,
docs/맞춤법 수비대 기획서.md의 4장, 7.4, 8장, 9장을 읽어 줘.

이번 단계 목표: 화면 없이, 정답 판정과 문제 데이터 검증을 테스트로 단단하게 만든다.

할 일
1. 문제 타입 정의(src/data 또는 src/judge): 기획서 8.1 JSON 형식 그대로.
   - 3단계에는 "고칠 곳 없음" 문제가 섞인다(7.4). 이 문제를 8.1 형식에 어떻게 나타낼지
     두세 가지 방법을 비교해서 먼저 나에게 물어봐 줘. 결정 뒤 기획서 8.1에도 반영한다.
2. src/judge/ 순수 함수
   - 맞춤법 판정: "선택한 보기"와 "직접 입력한 문자열"을 모두 받을 수 있는 구조(7.4, 직접 입력은 나중에 쓰임).
   - 틀린 낱말 찾기 판정: 학생이 탭한 위치가 target 범위에 들어가는지.
   - 띄어쓰기 판정(8.2): 문장을 음절 배열로 나누고 글자 사이 띄움/붙임 값을 비교. acceptedAnswers 중 하나와 같으면 정답.
     틀린 위치 목록(띄워야 할 곳, 붙여야 할 곳)을 돌려준다.
   - 문장 부호 판정.
   - 모든 비교 전에 NFC 정규화, 앞뒤 공백·연속 공백 처리.
3. Vitest 테스트: 정상 사례뿐 아니라 경계 사례를 넣는다.
   - NFD로 들어온 한글, 문장 끝 공백, 연속 공백, 복수 정답, 문장 부호 앞 띄어쓰기, 빈 입력
4. scripts/validate-problems.ts (9.1 ③ 자동 검증)
   - wrong ≠ correct, 차이가 target 한 곳뿐인지, target.start 위치의 글자가 wrongText와 같은지
   - choices에 정답이 정확히 하나인지
   - 띄어쓰기 문제는 공백 말고 글자가 같은지
   - 단계별 문장 길이 상한(9.3), id 중복, 필수 필드
   - 문제가 있는 항목을 파일 이름·id와 함께 출력하고 실패 코드로 끝낸다. npm run validate로 실행.
   - 이 검증 로직은 나중에 앱 안 AI 생성(M7)에서도 쓰므로 src/ 아래 모듈로 만들고 스크립트는 그것을 부른다.
5. 3단계 샘플 문제 30개 초안(src/data/problems/)
   - 기획서 4.2 3단계 태그에 고르게 나누고, 9.3 콘텐츠 원칙을 지킨다. 띄어쓰기 허용 규정(보조 용언 등)은 피한다.
   - 모두 "source": "builtin", "reviewed": false 로 둔다.
   - 확신이 낮은 문제는 별도로 표시해 목록으로 알려 줘.
   - 내가 검수하기 쉽게 docs/문제 검수표 M2.md에 표(번호, 태그, 틀린 문장, 바른 문장, 설명, 확신 낮음 표시)로도 정리한다.

하지 않을 일: 게임 화면 연결.
끝나면 npm test, npm run validate, npm run build 결과를 보여 주고, 진행 기록과 커밋을 남겨 줘.
```

> **검수 후**: 선생님이 검수표에서 고칠 문제를 알려 주고 "검수 끝난 문제는 reviewed를 true로 바꿔 줘"라고 요청합니다.

## M3. 개인 수비 모드 게임 루프

**추천 모델**: Sonnet 5.5 High (게임 루프 구조가 두 번 이상 꼬이면 Opus 5.5 Medium) · **확인 기준**: 한 스테이지를 처음부터 끝까지 플레이할 수 있음

```text
맞춤법 수비대 M3 단계를 시작하자.
docs/진행 기록.md, docs/맞춤법 수비대 단계별 프롬프트.md 0장,
docs/맞춤법 수비대 기획서.md의 6.1, 7장을 읽어 줘.

이번 단계 목표: M1 화면에 M2 판정 로직을 연결해서, 한 스테이지를 처음부터 끝까지 플레이할 수 있게 한다.

할 일
1. 게임 루프(src/game/): requestAnimationFrame 기반. 경과 시간(delta) 기준으로 움직여 기기 속도와 상관없이 같은 빠르기.
   - 웨이브 구성: 한 스테이지 8~12문제, 3개 레인에 나눠 등장. 몬스터는 느리게 시작.
   - 속도: 보통 / 느리게 / 일시정지. 탭 한 몬스터는 그동안 멈춘다.
   - 정답·규칙 설명이 떠 있는 동안 게임 전체가 멈춘다(7.2).
2. 고치기 흐름(7.4 3단계 기준, 단계 값에 따라 달라지게)
   - 맞춤법: 문장에서 틀린 낱말 탭 → 보기 3개 중 선택. "고칠 곳 없음" 버튼.
   - 띄어쓰기 칼: 글자 사이를 탭해 띄움/붙임 전환 → "자르기"로 확인. 틀리면 틀린 위치를 강조.
   - 문장 부호: 1단계용 미니 유형(샘플 문제가 있으면 연결, 없으면 테스트용 임시 문제 2개).
3. 결과 처리
   - 정답: 몬스터 정화 연출(CSS), 규칙 한 줄 표시, 마나 획득.
   - 오답: 바른 답과 설명을 보여 주고 몬스터는 계속 행진.
   - 성에 닿으면 성벽 낙서(임시 도형) + 성벽 체력 소폭 감소. 게임 오버 없이 끝까지 진행(7.2).
   - 모든 웨이브가 끝나면 결과 화면: 별 1~3개(성벽 상태 기준), 정화 수, 놓친 수.
4. 출제: reviewed: true 문제만. 아직 true가 적으면 개발 확인용으로만 쓰는 스위치를 두되, 기본값은 꺼짐.
5. 테스트: 게임 상태 변화(정답, 오답, 성 도달, 스테이지 종료, 별 계산)를 순수 함수로 분리해 Vitest로 확인.
   Playwright로 한 스테이지 끝까지 진행하는 흐름 테스트 하나.

하지 않을 일: 복습, 오답 노트, 저장, 실제 그림.
끝나면 진행 기록과 커밋을 남기고, 내가 직접 해 볼 확인 순서를 3~5줄로 알려 줘.
```

## M4. 복습, 오답 노트, 간격 반복, 로컬 저장

**추천 모델**: Sonnet 5.5 High · **확인 기준**: 브라우저를 닫았다 열어도 기록 유지

```text
맞춤법 수비대 M4 단계를 시작하자.
docs/진행 기록.md, docs/맞춤법 수비대 단계별 프롬프트.md 0장,
docs/맞춤법 수비대 기획서.md의 2.3, 5.1, 6.1, 7.1, 7.3, 11장을 읽어 줘.

이번 단계 목표: 학습이 쌓이게 만든다.

할 일
1. 저장(src/storage/): localStorage, 스키마 버전 필드 포함. 데이터가 깨졌거나 버전이 다르면 앱이 멈추지 않고 안전하게 초기화·변환.
   저장 구조(어떤 키에 무엇을 저장할지)를 먼저 짧게 보여 주고 시작해 줘.
2. 낙서 지우기(복습): 스테이지 끝난 뒤 놓치거나 틀린 문제를 시간 제한 없이 다시 풀기. 다 지우면 성벽 낙서가 사라지는 연출.
3. 오답 노트: 유형 태그별로 틀린 문제 정리, 태그마다 규칙 설명 카드.
4. 간격 반복: 오답 문제를 다음 스테이지에 다시 섞어 출제. 같은 태그를 3번 연속 맞히면 "익힘"으로 바꾸고 오답 노트에서 뺀다(2.3).
5. 스테이지 지도: 단계별(1단계 마을 → 2단계 숲 → 3단계 성), 별 기록, 다음 스테이지 열림.
   단계 선택 화면과 (선택) 닉네임 입력(기기에만 저장).
6. 몬스터 도감: 정화한 유형의 몬스터 카드(임시 그림) + 규칙 설명.
7. "내 기록 지우기" 버튼(확인 단계 포함, 11장).
8. 테스트: 저장·불러오기, 버전 변환, 간격 반복 규칙, 익힘 판정을 Vitest로.
   Playwright로 "플레이 → 새로고침 → 기록 유지" 확인.

하지 않을 일: 기록 내보내기(2단계 기능), 실제 그림.
끝나면 진행 기록과 커밋을 남겨 줘.
```

## M7. 교사 메뉴, API 키 입력, AI 문제 생성
