## 1. 개요

- **앱 이름**: 맞춤법 수비대 (Spell Defenders)
- **한 줄 소개**: 틀린 맞춤법을 들고 성으로 행진하는 "오타 몬스터"를 바르게 고쳐 정화하는 맞춤법·띄어쓰기 타워 디펜스 게임
- **대상**: 초등 2~6학년 학생, 그리고 수업에 활용하는 담임·국어 교사
- **교과 연계**: 국어(문법 영역 — 소리와 표기, 낱말, 문장 부호, 띄어쓰기)
- **사용 장면**
  - 학생 개인: 수업 마무리 10분, 아침 활동, 자투리 시간에 태블릿·크롬북으로 플레이
  - 학급 전체: 교사가 전자칠판에 띄우고 반 전체가 함께 몬스터를 막는 도입·정리 활동

## 2. 목표

### 2.1 교육 목표
1. 초등학생이 자주 틀리는 맞춤법(되/돼, 안/않, 로서/로써, 소리와 표기가 다른 낱말 등)을 **반복 노출과 즉각 피드백**으로 바르게 익힌다.
2. 띄어쓰기의 기본 원칙(낱말 단위 띄어쓰기, 조사 붙여 쓰기, 의존 명사·단위 띄어 쓰기 등)을 **직접 문장을 잘라 보는 활동**으로 체득한다.
3. 틀린 이유를 **아이 눈높이의 규칙 설명**(예: "'되어'로 바꿔 말이 되면 '돼'")과 함께 익혀, 게임 밖 글쓰기에서도 스스로 고칠 수 있게 한다.

### 2.2 제품 목표
- 설치·로그인 없이 링크 하나로 바로 시작할 수 있다.
- 한 판(스테이지)이 **3~5분** 안에 끝나 수업 시간에 끼워 넣기 쉽다.
- 교사가 자기 반 학생들이 자주 틀리는 문장을 **5분 안에 문제로 만들어 배포**할 수 있다.

### 2.3 성공 기준 (파일럿 수업 기준)
- 파일럿 학급(5학년) 학생이 설명 없이 첫 스테이지를 시작·완료할 수 있다.
- 같은 오류 유형을 3회 이상 연속으로 맞히면 "익힘"으로 판정되고, 오답 노트에서 빠진다.
- 파일럿 학급에서 사전·사후 간이 평가(20문항)로 정답률 변화를 측정한다. (원 조사 문서 권고: 한국어 맞춤법에 대한 직접 연구가 없으므로 자체 검증 필요)

### 2.4 파일럿 계획
| 항목 | 내용 |
|---|---|
| 대상 | 5학년 우리 반 (2학기) |
| 시간 | 국어 시간(단원 도입·정리 10분), 창체 시간(한 차시 전체 활용 가능) |
| 기기 | 학생 디벗(크롬북, 1920×1080) + 교실 전자칠판 |
| 콘텐츠 | 3단계(초5~6) 문제 우선. 1·2단계는 파일럿 뒤 확장 |
| 측정 | 사전 평가 → 2~3주 사용(주 2~3회) → 사후 평가, 학생 소감 설문 |
| 일정 | 개인 수비 모드 완성(M5) 뒤 짧은 첫 테스트 → 조정 → 본 파일럿 (12.1~12.2) |

## 3. 교육적 근거와 한계

| 근거 | 내용 | 기획에 반영한 점 |
|---|---|---|
| 독일 초등 116명 RCT (Prosodiya) | 9~10주 디지털 게임 기반 철자 훈련으로 철자 능력 향상, 난독·비난독 아동 모두 포함 | 단기 이벤트가 아닌 **주 2~3회, 수 주간 반복 사용** 루틴 설계 |
| 2025 협동형 철자 게임 연구 | 협동형 게임이 개인형·전통적 방법보다 효과적 | 협동 모드는 2단계로 미루되, MVP에서도 **학급 전체 모드**로 협동 경험 제공 |
| 41개 연구 게이미피케이션 메타분석 | 큰 긍정 효과, 설계 원칙·지속 기간이 효과 조절 | 처벌 최소화, 짧은 스테이지, 지속 사용을 유도하는 수집 요소 |
| 리뷰 연구 공통 비판 | 교육용 게임이 교육 내용과 통합되지 않음 | **오류 유형 태그를 교육과정·한글 맞춤법 조항에 1:1 매핑** (4장) |

**한계**: 근거 연구는 독일어 철자 대상이며, 한국어 맞춤법·띄어쓰기를 직접 다룬 게임 효과 연구는 이번 조사에서 확인하지 못했습니다. 초등학생 맞춤법 오류 실태도 학술 연구보다는 출판사 설문(학부모 320명 대상, ㅐ/ㅔ 혼동 64%, 이어서 안/않·되/돼·ㅢ/ㅔ·받침 혼동) 위주라 근거가 약합니다. 따라서 **파일럿 측정**을 기획에 포함합니다.

## 4. 학습 내용 체계

### 4.1 교육과정 연계 (2022 개정 국어과, 문법 영역)

| 학년군 | 관련 성취기준 (검색으로 확인한 문구) | 앱에서 다룰 내용 |
|---|---|---|
| 1~2학년 | [2국04-02] 소리와 표기가 다를 수 있음을 알고 단어를 바르게 읽고 쓴다. / 문장 부호를 알맞게 쓰는 성취기준(교육청 자료에서 확인, 번호 원문 대조 필요) | 소리와 표기가 다른 낱말, 받침, 마침표·물음표·느낌표 |
| 3~4학년 | [4국04-01] 낱말을 분류하고 국어사전에서 찾는다. / [4국04-03] 기본적인 문장의 짜임을 이해하고 사용한다. | 헷갈리는 낱말, 낱말 단위 띄어쓰기, 조사 붙여 쓰기 |
| 5~6학년 | [6국04-04] 문장 성분을 이해하고 호응 관계가 올바른 문장을 구성한다. (출처 간 번호 불일치) | 구별해 써야 하는 말, 의존 명사·보조 용언 띄어쓰기 |

> ⚠️ 성취기준 번호와 문구는 출처마다 차이가 있었습니다. 개발 전에 **국가교육과정정보센터(ncic.re.kr) 고시 원문**과 현재 사용하는 국어 교과서 단원으로 대조해 확정해야 합니다.

**교과서 연계 방식**: 앱의 스테이지는 교과서 단원이 아니라 **오류 유형별**로 구성합니다. 대신 「교사용 안내」(`docs/`에 별도 문서)에 **학년·학기별 국어 교과서 단원 ↔ 유형 태그 연결표**를 실어, 교사가 "이 단원 수업 뒤에는 이 스테이지"를 골라 쓸 수 있게 합니다. 파일럿을 위해 **5학년 2학기 연결표**를 가장 먼저 만듭니다.

### 4.2 오류 유형 태그 체계 (안)

모든 문제는 아래 **유형 태그** 하나를 가지며, 오답 노트와 진도 관리는 이 태그 단위로 이루어집니다. 조항 번호는 국립국어원 「한글 맞춤법」 기준이며, 콘텐츠 검수 단계에서 원문과 다시 대조합니다.

**1단계 (초2) — 소리와 표기**

| 태그 | 예시 (틀림 → 바름) | 근거 |
|---|---|---|
| 소리 나는 대로 쓰기 | 가치 놀자 → 같이 놀자, 구지 → 굳이 | 제1항, 제6항(구개음화) |
| 받침 | 닥 → 닭, 일따 → 읽다 | 소리와 표기 |
| ㅐ/ㅔ | 배개 → 베개, 께끗이 → 깨끗이 | 표기 |
| 된소리 | 할께 → 할게, 할꺼야 → 할 거야 | 제53항 |
| 문장 부호 | 밥 먹었니. → 밥 먹었니? | 문장 부호 규정 |
| 띄어쓰기 기초 | 나는학교에간다 → 나는 학교에 간다 | 제2항 |

**2단계 (초3~4) — 헷갈리는 낱말**

| 태그 | 예시 | 아이용 규칙 설명 |
|---|---|---|
| 되/돼 | 열 살이 되요 → 열 살이 돼요 | '되어'로 바꿔 말이 되면 '돼' |
| 안/않 | 숙제를 하지 안았다 → 숙제를 하지 않았다 | '아니'로 바꿀 수 있으면 '안', '아니하'면 '않' |
| 자주 틀리는 낱말 | 몇일 → 며칠, 금새 → 금세, 설겆이 → 설거지, 역활 → 역할, 일부로 → 일부러 | 낱말별 설명 |
| 뜻이 다른 낱말 | 잊어버리다/잃어버리다, 가르치다/가리키다, 낫다/낮다/낳다 | 뜻 구별 |
| 조사 붙여 쓰기 | 친구 와 함께 → 친구와 함께 | 제41항 |
| 단위 띄어쓰기 | 사과한개 → 사과 한 개 | 제43항 |

**3단계 (초5~6) — 구별해 쓰는 말과 띄어쓰기 심화**

| 태그 | 예시 | 근거 |
|---|---|---|
| 로서/로써 | 반장으로써 책임을 다했다 → 반장으로서 | 제57항 |
| 든지/던지 | 사과든지 배든지 / 얼마나 춥던지 | 제56항 |
| 맞히다/맞추다 | 정답을 맞췄다 → 정답을 맞혔다 | 제57항 |
| 붙이다/부치다, 반드시/반듯이 | 편지를 붙였다 → 편지를 부쳤다 | 제57항 |
| 웬/왠 | 왠일이니 → 웬일이니 (단, '왠지'는 바름) | 표기 |
| 어떡해/어떻게 | 어떻해 → 어떡해 | 표기 |
| -이/-히 | 깨끗히 → 깨끗이 | 제51항 |
| 사이시옷 | 나뭇잎, 바닷가, 햇빛 | 제30항 |
| 의존 명사 띄어쓰기 | 할수있다 → 할 수 있다, 먹을것 → 먹을 것 | 제42항 |
| 보조 용언 | 먹어 보다 / 먹어보다 (둘 다 허용) | 제47항 — **허용 규정 주의** |

> 띄어쓰기에는 **두 가지 모두 허용되는 경우**(보조 용언, 전문 용어 등)가 있습니다. 이런 문장은 문제로 내지 않거나, 두 답을 모두 정답 처리해야 합니다. 이 규칙을 문제 데이터 형식에 반영합니다(8장 `acceptedAnswers`).

## 5. 사용자와 사용 시나리오

### 5.1 학생 (개인 모드)
1. 링크 접속 → 학년군(단계) 선택 → (선택) 닉네임 입력
2. 지도에서 스테이지 선택 → 3~5분 수비전
3. 놓친 몬스터의 "낙서 지우기" 복습
4. 별·도감 보상 확인 → 다음 스테이지 열림
5. 언제든 "오답 노트"에서 내가 틀린 유형 확인

### 5.2 교사 (학급 전체 모드)
1. 전자칠판에서 "학급 수비전" 선택 → 단계·유형 선택
2. 몬스터가 한 마리씩 크게 등장 → 학생들이 손을 들거나 모둠별로 답 발표
3. 교사가 정답을 터치 → 규칙 설명 카드를 함께 읽음
4. 기록은 남기지 않음 (학급 점수만 화면에 표시)

### 5.3 교사 (문제 관리)
1. 교사 메뉴 진입 (간단한 PIN)
2. (처음 한 번) **내 OpenRouter API 키 입력** 화면에서 키를 붙여 넣고 모델 선택 (10.4)
3. AI로 문제 만들기: 단계·유형·개수 선택 → 생성 결과를 하나씩 **승인 / 수정 / 삭제**
4. 문제 세트 이름을 붙여 저장 → **공유 코드(링크·QR)** 생성
5. 학생은 링크나 QR로 그 문제 세트를 자기 기기에 불러옴

> 서버가 없으므로 교사가 만든 문제는 교사 기기에만 저장됩니다. 학생 기기로 옮기는 방법이 **공유 코드(문제 세트를 압축해 URL에 담기)**이며, 이것이 서버 없는 구조의 핵심 설계입니다.

### 6.1 MVP (1단계 개발)

## 7. 게임 디자인

### 7.1 핵심 루프

```
스테이지 시작
  → 오타 몬스터가 3개 길(레인)을 따라 성으로 행진
  → 몬스터 탭 → 문장 카드 확대 (그 몬스터는 잠시 멈춤)
  → 틀린 곳 찾기 → 고치기
      ├ 정답: 몬스터 정화 ✨ + 규칙 한 줄 표시 + 마나(점수) 획득
      └ 오답: 바른 답과 규칙 설명을 보여 줌 → 몬스터는 계속 행진
  → 성에 닿은 몬스터: 성벽에 "낙서" (성벽 체력 소폭 감소)
  → 모든 웨이브 종료 → 별 1~3개 (성벽 상태 기준)
  → 낙서 지우기 복습
  → 보상: 별, 몬스터 도감 등록, 다음 스테이지 열림
```

### 7.2 설계 원칙
- **처벌 최소화**: 성벽이 무너져도 "게임 오버" 없이 스테이지는 끝까지 진행되고, 낙서 지우기로 복구할 수 있습니다.
- **오답 = 학습 기회**: 틀렸을 때 바로 정답과 규칙을 보여 줍니다. 시간 압박 때문에 설명을 못 읽는 일이 없도록 설명이 떠 있는 동안 게임이 멈춥니다.
- **읽기 속도 배려**: 실시간이지만 몬스터 이동은 느리게 시작하고, 학생이 직접 "느리게"를 고를 수 있습니다.
- **짧은 스테이지**: 한 스테이지 8~12문제, 3~5분.

### 7.3 보상 요소
- **몬스터 도감**: 오류 유형마다 다른 몬스터(예: "갈림길 거북" = 로서/로써, "찰싹 애벌레" = 띄어쓰기, 전체 목록은 16.3). 정화하면 도감에 등록되고, 도감 카드에 규칙 설명이 들어 있어 **보상이 곧 학습 자료**가 됩니다. 몬스터마다 "오타 상태"와 "정화 상태" 두 가지 그림을 둡니다.
- **별과 스테이지 지도**: 단계별 지도(1단계 마을 → 2단계 숲 → 3단계 성).
- **수비 타워 업그레이드**(검토): 많이 정화할수록 성 장식이 바뀌는 정도로 단순하게.

### 7.4 고치는 방식 (입력 방식)
태블릿에서 한글을 직접 타이핑하는 것은 느리고 입력기(IME) 문제도 많아서, **MVP는 선택형**으로 설계합니다.

| 단계 | 맞춤법 | 띄어쓰기 |
|---|---|---|
| 1단계 | 틀린 낱말이 표시된 상태에서 보기 2개 중 선택 | 낱말 3~4개짜리 짧은 문장 |
| 2단계 | 틀린 낱말을 직접 찾아 탭 → 보기 3개 중 선택 | 조사·단위가 섞인 문장 |
| 3단계 | 틀린 곳이 없는 문장도 섞임("고칠 곳 없음" 버튼) | 의존 명사가 들어간 긴 문장 |

> 5~6학년용 **직접 입력 모드**(틀린 낱말을 키보드로 고쳐 쓰기)는 MVP 이후 업데이트로 추가합니다(17장). 이를 대비해 판정 로직(`judge/`)은 처음부터 "선택한 보기"와 "입력한 문자열"을 모두 받을 수 있는 구조로 만듭니다.

## 8. 문제 데이터 설계

### 8.1 문제 형식 (JSON)

```json
{
  "id": "L2-doe-001",
  "level": 2,
  "kind": "spelling",
  "tag": "되/돼",
  "rule": "한글 맞춤법 제35항 붙임 2",
  "wrong": "내일이면 열 살이 되요.",
  "correct": "내일이면 열 살이 돼요.",
  "target": { "wrongText": "되요", "start": 10 },
  "choices": ["돼요", "되요", "돼여"],
  "acceptedAnswers": ["내일이면 열 살이 돼요."],
  "explain": "'되어요'로 바꿔도 말이 되니까 '돼요'가 맞아요.",
  "source": "builtin",
  "reviewed": true
}
```

| 필드 | 설명 |
|---|---|
| `kind` | `spelling`(맞춤법) / `spacing`(띄어쓰기) / `punctuation`(문장 부호) |
| `tag` | 4.2의 오류 유형 태그. 오답 노트·도감·진도의 기준 |
| `target` | 틀린 부분의 위치. 띄어쓰기 문제는 생략하고 `wrong`과 `correct`의 띄어쓰기 위치를 비교 |
| `acceptedAnswers` | 두 가지가 모두 허용되는 띄어쓰기 등 복수 정답 |
| `source` | `builtin`(내장) / `ai`(교사 AI 생성) / `teacher`(교사 수정) |
| `reviewed` | 교사 승인 여부. **`false`인 문제는 학생에게 절대 출제하지 않음** |

### 8.2 띄어쓰기 판정
- 문장을 글자(음절) 배열로 나누고, 각 글자 사이에 "띄움/붙임" 값을 두어 비교합니다.
- 학생 답의 띄움 위치 집합이 `acceptedAnswers` 중 하나와 일치하면 정답입니다.
- 틀린 위치만 골라 강조해 보여 줍니다 ("여기는 띄어야 해요").
- 한글 문자열은 비교 전에 유니코드 NFC 정규화를 합니다.

### 8.3 문제은행 규모 목표
- 단계당 유형 6~10개 × 유형당 20문제 → 단계당 약 120~200문제, **전체 약 400~600문제**
- MVP는 단계당 60문제 정도로 시작해 파일럿 후 확장

## 9. 콘텐츠 제작 프로세스

맞춤법 앱에서 **정답이 틀리는 것이 가장 치명적인 결함**입니다. 원 조사 문서도 "LLM으로 만든 문장은 정답 자체가 틀릴 위험이 있으므로 교사 검수 필수"라고 경고합니다.

### 9.1 개발 단계 (내장 문제은행)
```
① 유형별 생성 지침 작성 (4.2 태그·예시·금지 사항)
② Claude로 유형별 문제 초안 대량 생성 (JSON)
③ 자동 검증 스크립트
   - wrong ≠ correct, 차이가 target 위치 한 곳뿐인지
   - choices에 정답이 정확히 하나 들어 있는지
   - 띄어쓰기 문제는 띄어쓰기 외에 글자가 같은지
   - 문장 길이가 단계별 상한 이내인지
④ 표준국어대사전·한국어 어문 규범(korean.go.kr)으로 사람이 검수
⑤ 교사(사용자) 최종 승인 → reviewed: true
```

### 9.2 앱 안 교사 생성 (2단계 개발)
- 교사가 단계·유형·개수·(선택) 소재를 입력 → AI가 8.1 형식 JSON으로 생성
- 9.1의 자동 검증 ③을 앱 안에서 똑같이 실행해, 형식이 틀린 문제는 자동 제외
- 생성 문제는 모두 `reviewed: false`로 들어가고, 교사가 하나씩 승인해야 출제
- 교사가 문장을 직접 고칠 수 있는 편집 화면 제공 (사실상 "교사 직접 입력" 기능 겸용)

### 9.3 콘텐츠 원칙
- 학생 일상 소재(학교, 급식, 친구, 가족, 운동회 등) 사용, 실존 인물·브랜드 금지
- 문장 길이: 1단계 15자 이하, 2단계 25자 이하, 3단계 40자 이하 (안)
- 틀린 문장에 **오류는 하나만** 넣기 (여러 오류는 혼란을 줌)
- 허용 규정이 있는 띄어쓰기는 문제로 쓰지 않거나 복수 정답 처리

## 10. 기술 스택과 구조

### 10.1 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 프레임워크 | **React 18 + Vite + TypeScript** | 서버 없는 정적 사이트, 빠른 개발 서버 |
| 게임 화면 | DOM + CSS transform + `requestAnimationFrame` | 문장(한글 텍스트)이 핵심이라 Canvas보다 DOM이 글자 표시·접근성·터치 처리에 유리. 스프라이트는 투명 배경 PNG/WebP를 `<img>`로 올리고 걷기·흔들림은 CSS 애니메이션으로 표현 |
| 상태 관리 | React `useReducer` + Context (필요 시 Zustand) | 규모가 작아 외부 라이브러리 최소화 |
| 저장 | `localStorage` (스키마 버전 필드 포함) | 로그인 없음, 기기 저장 결정 |
| 공유 코드 | `lz-string`(URL 압축) + `qrcode`(QR 생성) | 서버 없이 문제 세트 전달 |
| AI 호출 | 브라우저에서 **OpenRouter** API 직접 호출 (`https://openrouter.ai/api/v1/chat/completions`) | 키는 사용자가 앱에서 직접 입력. 코드·`.env`·저장소에 키를 넣지 않음 |
| 글꼴 | Pretendard 등 가독성 좋은 웹폰트 | 저학년 가독성, 전자칠판 큰 글씨 |
| 효과음 | Web Audio API (짧은 효과음 몇 개) | 별도 라이브러리 불필요 |
| 테스트 | Vitest(판정·검증 로직), Playwright(주요 흐름) | 정답 판정 오류 방지가 최우선 |
| 배포 | Vercel 또는 GitHub Pages | 무료, 링크 하나로 배포 |

### 10.3 화면 대응

| 기기 | 해상도 | 우선순위 |
|---|---|---|
| **디벗 크롬북 (파일럿 학급 학생 기기)** | **1920×1080 (FHD)** | 1순위 기준 화면 |
| 크롬북·노트북 HD | **1366×768** | 1순위와 함께 반드시 확인 |
| 전자칠판 (학급 모드) | 1920×1080 | 학급 모드 기준 |
| 태블릿 가로 | 1024×768 이상 | 참고 (깨지지 않는 정도) |

- **16:9 가로 화면 고정 설계**: 게임 무대는 16:9 비율로 만들고 화면 크기에 맞춰 통째로 확대·축소합니다. 1920×1080과 1366×768은 둘 다 16:9에 가까워(1366×768은 약 16:9) 같은 배치가 그대로 맞습니다.
- **실제 보이는 영역 고려**: 크롬북 브라우저는 주소창·탭·작업 표시줄 때문에 실제 화면이 더 작습니다(1366×768에서 약 1366×650 내외). 세로 공간이 부족하므로 **전체 화면 버튼**(Fullscreen API)을 시작 화면에 두고, 전체 화면이 아닐 때도 문장 카드와 보기 버튼이 잘리지 않게 합니다.
- **크롬북 화면 배율**: 크롬북은 기본 배율 설정 때문에 1920×1080 기기도 브라우저에서는 더 작은 해상도(예: 1536×864)로 보일 수 있습니다. 그래서 픽셀 고정값이 아니라 **화면 비율 기준으로 배치**하고, 개발 중 1920×1080, 1536×864, 1366×768 세 크기에서 확인합니다.
- **글자 크기**: 문장 카드 글자는 1366×768에서도 최소 24px 이상(실제 표시 기준), 학급 모드는 그 2배 이상
- **입력 방식**: 디벗은 터치스크린과 트랙패드·키보드를 함께 쓸 수 있으므로 **터치와 마우스 클릭 모두** 지원(포인터 이벤트 사용). 터치 영역 최소 48px

### 10.4 추천 AI 모델 (OpenRouter)

이 앱에서 AI가 하는 일은 **짧은 한국어 문장 생성 + 맞춤법 정답 판단 + 정해진 JSON 형식 지키기**입니다. 긴 추론이나 코딩 능력보다 **한국어 맞춤법 정확성과 형식 준수**가 중요하고, 한 번에 생성하는 양이 적어 비용 부담은 크지 않습니다.

| 순서 | 모델 | OpenRouter 모델 ID | 가격 (100만 토큰당, 입력 / 출력) | 추천 이유 |
|---|---|---|---|---|
| 1 | **Claude Sonnet 5.5** | `anthropic/claude-sonnet-5.5` | $2 / $10 | 미묘한 규칙 구분(로서/로써, 의존 명사 띄어쓰기)과 아이 눈높이 설명 작성에 강한 중상급 모델. **기본 모델(품질 우선)** |
| 2 | **Gemini 3.8 Flash** | `google/gemini-3.8-flash` | $0.75 / $3.75 | Sonnet의 약 3분의 1 가격, 최신 Flash 중 가장 성능이 높음. **품질과 비용의 균형** |
| 3 | **GPT-6 Luna** | `openai/gpt-6-luna` | $0.1 / $0.5 | GPT-6 시리즈의 빠르고 저렴한 모델. Sonnet의 20분의 1 가격. **비용 최소화** |

- 앱의 모델 선택 목록도 위 순서(Sonnet 5.5 → Gemini 3.8 Flash → GPT-6 Luna)로 보여 주고, 첫 번째를 기본 선택으로 둡니다.
- 가격과 모델 ID는 2026-10-09 OpenRouter 모델 목록 API로 확인했습니다. 세 모델 모두 OpenRouter에서 `structured_outputs`(JSON 스키마 강제)를 지원하므로 8.1 형식을 안정적으로 받을 수 있습니다.
- **1회 비용 예상** (문제 20개 생성, 입력 약 2천 토큰 + 출력 약 4천 토큰 가정, 1달러 약 1,400원): Sonnet 5.5 약 $0.044(약 60원), Gemini 3.8 Flash 약 $0.017(약 25원), GPT-6 Luna 약 $0.002(약 3원). 추론(reasoning) 토큰이 더해지면 늘어나므로 추론 강도는 `low`로 둡니다.
- 한국어 맞춤법 정확도를 직접 비교한 공개 벤치마크는 확인하지 못했습니다. 특히 GPT-6 Luna는 소형 모델이라 미묘한 맞춤법 판단에서 오류가 더 나올 수 있으므로, **같은 지침으로 세 모델에서 문제 20개씩 생성해 오류율을 비교**합니다. 어떤 모델을 쓰든 교사 승인 단계(9.2)는 그대로 거칩니다.
- 중국산 모델은 목록에 넣지 않습니다.
- 모델이 바뀌어도 쓸 수 있도록 **모델 ID 직접 입력** 칸을 둡니다.

## 11. 개인정보와 안전

- **학생 개인정보를 수집하지 않습니다.** 로그인·서버 저장 없음, 닉네임은 선택이며 기기에만 저장
- **OpenRouter API 키 처리 원칙**
  - 앱 코드, `.env`, 깃 저장소, 배포 설정 어디에도 키를 넣지 않습니다. 키는 사용자가 앱의 입력 화면에 **직접 붙여 넣을 때만** 존재합니다.
  - 기본값은 **이번 접속에서만 기억**(sessionStorage, 브라우저를 닫으면 삭제). "이 기기에 저장"을 직접 체크한 경우에만 localStorage에 저장합니다. 공용 기기에서 키가 남지 않게 하기 위해서입니다.
  - 입력 칸은 비밀번호 형식(가림 표시), "키 지우기" 버튼 제공
  - 키는 OpenRouter 외 다른 곳으로 전송하지 않습니다.
  - OpenRouter에서 키별 사용 한도(credit limit)를 걸어 두도록 안내 문구 제공
- 교사 메뉴는 PIN으로 가립니다. (PIN은 클라이언트 쪽 장치라 학생의 우발적 접근을 막는 정도의 보호임을 안내)
- 학생 기기에는 API 키가 필요 없도록 설계 (학생은 공유 코드로 문제만 받음)
- 공용 기기에서 여러 학생이 쓸 경우를 위해 "내 기록 지우기" 버튼 제공

## 12. 개발 로드맵

### 12.1 일정 원칙: 천천히, 작은 단위로

정해진 마감은 없습니다. 당장 수업에 써야 하는 앱이 아니므로, **업무 사이사이에 짧게 개발하고 → 완성된 부분을 확인하고 → 수업 현장에서 시험한 뒤 → 조정하는** 방식으로 천천히 진행합니다.

- **한 번에 한 덩어리**: 개발은 아래 12.2의 작은 단위(마일스톤) 하나씩 진행합니다. 한 단위는 한두 번의 작업 시간 안에 끝나고, 끝날 때마다 **그 상태로 실행해 볼 수 있게** 만듭니다. 중간에 쉬었다가 다시 시작해도 이어 가기 쉽도록 단위마다 진행 기록을 `docs/`에 남깁니다.
- **선생님 손이 필요한 일은 미리, 여유 있게**: 문제 검수(3단계 80개 이상)와 그림 제작(21장)은 개발과 별개로 시간이 날 때 조금씩 진행합니다. 그림이 준비되기 전에는 임시 그림(단색 도형)으로 개발하고 나중에 바꿔 끼웁니다.
- **현장 투입은 단계적으로**: 첫 학교 테스트는 개인 수비 모드가 완성된 뒤 짧게(10~15분) 해 보고, 조정을 거쳐 본 파일럿(2.4, 사전·사후 평가 포함)으로 넘어갑니다.

## 16. 그림 리소스 제작 계획 (나노바나나)

이모지를 쓰지 않고 처음부터 배경과 캐릭터 스프라이트를 만듭니다. 아래 프롬프트를 **Gemini 앱(나노바나나)**에 그대로 복사해 쓰면 됩니다. 프롬프트는 이미지 모델이 더 잘 이해하도록 영어로 작성했습니다.

### 16.0 제작 원칙
- **그림 안에 글자를 넣지 않습니다.** 이미지 모델은 한글을 자주 틀리게 그리고, 맞춤법 앱에서 그림 속 글자가 틀리면 치명적입니다. 문장·이름표는 모두 앱이 글자로 표시합니다. (모든 프롬프트에 `no text, no letters` 포함)
- **스프라이트는 단색 배경으로 생성 → 배경 제거**: 나노바나나는 투명 배경을 안정적으로 만들지 못하므로 순수한 흰 배경으로 만든 뒤 배경 제거 도구(remove.bg, 캔바, 포토샵 등)로 투명 PNG를 만듭니다.
- **한 장에 한 캐릭터, 한 자세**: 여러 프레임을 한 장에 그린 스프라이트 시트는 프레임마다 모양이 달라지기 쉽습니다. 몬스터는 "오타 상태"와 "정화 상태" 두 장만 만들고, 걷기·흔들림·정화 효과는 앱에서 CSS 애니메이션으로 표현합니다.
- **그림체 통일**: 16.1 공통 스타일 문구를 모든 프롬프트 맨 앞에 붙입니다. 첫 몬스터가 마음에 들게 나오면, 그 이미지를 **참고 이미지로 첨부**하고 "같은 그림체로"라고 덧붙여 나머지를 만듭니다.
- **파일 규격**: 배경 16:9(1920×1080 이상), 캐릭터 1:1(1024×1024). 앱에 넣을 때 WebP로 변환해 용량을 줄입니다.

### 16.1 공통 스타일 문구 (모든 프롬프트 앞에 붙이기)

```
Art style: cute 2D cartoon game art for elementary school children, thick clean dark outlines, flat bright colors with soft cel shading, rounded friendly shapes, storybook fantasy kingdom theme, cheerful and not scary, consistent lighting from top-left. No text, no letters, no numbers, no watermark.
```

### 16.2 배경 (3장)

단계별 지도 테마에 맞춘 수비전 배경입니다. 몬스터가 왼쪽에서 오른쪽 성으로 걸어오므로 **가운데에 가로로 긴 길 3줄**, 오른쪽 끝에 성문 자리를 비워 둡니다.

**① 1단계 마을 (`bg-village`)**
```
[공통 스타일 문구]
A wide side-view game background of a peaceful storybook village meadow. Three parallel horizontal dirt paths run from the left edge toward the right edge, evenly spaced from the middle to the lower part of the image. Small cottages with colorful roofs, flower patches, and round trees in the far background. Leave the right edge of the image empty and plain for a castle gate that will be placed later. Leave the top area as soft blue sky with a few clouds, uncluttered, for game UI. 16:9 aspect ratio.
```

**② 2단계 숲 (`bg-forest`)**
```
[공통 스타일 문구]
A wide side-view game background of a bright magical forest. Three parallel horizontal forest trails run from the left edge toward the right edge, evenly spaced from the middle to the lower part of the image. Tall round trees, mushrooms, ferns, and soft sunbeams through the leaves. Leave the right edge empty and plain for a castle gate that will be placed later. Keep the top area simple and slightly lighter for game UI. 16:9 aspect ratio.
```

**③ 3단계 성 앞 (`bg-castle`)**
```
[공통 스타일 문구]
A wide side-view game background of the grand courtyard in front of a fantasy castle at golden sunset. Three parallel horizontal stone-paved roads run from the left edge toward the right edge, evenly spaced from the middle to the lower part of the image. Banners without any symbols or letters, lanterns, and distant mountains. Leave the right edge empty and plain for a castle gate that will be placed later. Keep the top area simple for game UI. 16:9 aspect ratio.
```

### 16.3 오타 몬스터 (MVP: 3단계 우선 6종 × 2장)

파일럿이 5학년이므로 3단계 유형 몬스터부터 만듭니다. 각 몬스터는 유형의 특징을 **모양**으로 표현합니다(글자로 표현하지 않음).

| 파일 이름 | 몬스터 | 유형 태그 | 모양 아이디어 |
|---|---|---|---|
| `mon-roseo` | 갈림길 거북 | 로서/로써 | 등딱지에 두 갈래 길 무늬, 어느 쪽으로 갈지 헷갈리는 표정 |
| `mon-maja` | 과녁 두더지 | 맞히다/맞추다 | 머리에 과녁 모자, 퍼즐 조각을 들고 있음 |
| `mon-buchi` | 우표 문어 | 붙이다/부치다 | 다리마다 봉투와 반창고가 붙어 있음 |
| `mon-wen` | 물음표 박쥐 | 웬/왠 | 귀가 물음표처럼 휘어 있음, 고개를 갸웃함 |
| `mon-saisiot` | 사이 거미 | 사이시옷 | 두 나뭇잎 사이에 작은 실을 잇고 있는 거미 |
| `mon-spacing` | 찰싹 애벌레 | 띄어쓰기 | 몸 마디가 서로 딱 붙어 엉켜 있음(정화되면 마디가 가지런히 떨어짐) |

**오타 상태 프롬프트 (예: 갈림길 거북)**
```
[공통 스타일 문구]
A single game character sprite: a small mischievous turtle monster whose shell has a pattern of a path splitting into two directions. It looks confused and a little naughty, walking toward the right side, full body, side view facing right. Slightly dusty purple and gray color tones to show it is "corrupted". Centered, plenty of margin around it, on a pure plain white background, no shadow on the ground. 1:1 aspect ratio.
```

**정화 상태 프롬프트 (같은 몬스터)** — 오타 상태 이미지를 첨부하고 사용
```
[공통 스타일 문구]
Using the attached character as reference, draw the SAME character in the same art style and same proportions, now purified and happy: bright clean pastel colors, sparkling eyes, a gentle smile, small sparkles around it, facing the viewer. Centered, plenty of margin, on a pure plain white background, no shadow. 1:1 aspect ratio.
```

> 다른 몬스터는 오타 상태 프롬프트에서 `A single game character sprite:` 뒤의 설명 한 문장만 위 표의 "모양 아이디어"로 바꾸면 됩니다. 두 번째 몬스터부터는 첫 몬스터 이미지를 첨부하고 `in the same art style as the attached image`를 덧붙입니다.

1·2단계 몬스터(되/돼, 안/않, ㅐ/ㅔ, 받침, 된소리, 조사 붙여 쓰기 등)는 파일럿 뒤 같은 방법으로 추가합니다.

### 16.4 수비대원과 성

**수비대원 (`char-defender`)** — 화면 오른쪽 성 위에서 몬스터를 정화하는 플레이어 캐릭터
```
[공통 스타일 문구]
A single game character sprite: a brave and friendly child guardian of about 11 years old, wearing a light blue cape and a small golden helmet, holding a magic quill pen that glows at the tip like a wand. Gender-neutral appearance, warm smile, full body, standing pose facing left. Centered, plenty of margin, on a pure plain white background, no shadow. 1:1 aspect ratio.
```

**수비대원 정화 동작 (`char-defender-cast`)** — 위 이미지를 첨부하고 사용
```
[공통 스타일 문구]
Using the attached character as reference, draw the SAME character in the same style, now casting a spell: pointing the glowing quill pen forward to the left, cape fluttering, a burst of sparkles from the pen tip. Full body, facing left. Centered, on a pure plain white background, no shadow. 1:1 aspect ratio.
```

**성문 (`castle-gate`)** — 배경 오른쪽 끝에 겹쳐 놓는 성
```
[공통 스타일 문구]
A single game object sprite: the side of a cute fairy-tale castle tower with a wooden gate, seen from the side, the gate facing left. Light stone walls, a blue cone roof, a small flag with no symbols. The wall must be completely clean with no drawings. Centered, on a pure plain white background, no shadow. Portrait 2:3 aspect ratio.
```

**성벽 낙서 (`graffiti-1`~`3`)** — 놓친 몬스터가 남기는 낙서, 성문 위에 겹쳐 표시
```
[공통 스타일 문구]
A single sticker-like graffiti doodle: messy purple crayon scribbles and a silly swirl shape, like a child's mischievous doodle, with no letters, no numbers, and no recognizable symbols. Centered, on a pure plain white background. 1:1 aspect ratio.
```
(3장 정도 만들어 무작위로 표시)

### 16.5 시작 화면

시작 화면(제목 화면) 이미지는 앱 제목 글자가 들어가야 하므로 별도 스킬(`make-homescreen`)로 프롬프트를 만듭니다. 그림 속 제목 글자가 틀리게 나오면 앱 쪽에서 글자로 다시 얹는 방법을 씁니다.

### 16.6 MVP 그림 체크리스트

| 구분 | 파일 | 수량 |
|---|---|---|
| 배경 | `bg-village`, `bg-forest`, `bg-castle` | 3 |

| 수비대원 | 기본, 정화 동작 | 2 |
| 성 | 성문, 낙서 3종 | 4 |
| **합계** | | **21장** |

## 17. 업데이트 예정 목록

MVP 이후 추가하기로 결정한 기능입니다. 파일럿 결과를 보고 순서를 정합니다.

| 기능 | 결정 내용 | 구현 메모 |
|---|---|---|
| **5~6학년용 직접 입력 모드** | MVP 이후 추가 | 판정 로직은 MVP부터 입력 문자열을 받을 수 있게 설계(7.4). 한글 입력기 조합 중(`compositionstart`~`compositionend`)에는 판정하지 않도록 처리 |
| **문장 읽어주기(TTS)** | MVP에서 구현하지 않음 | 저학년용. 브라우저 내장 Web Speech API(`speechSynthesis`)로 시작 가능하나 기기별 음성 품질 차이 확인 필요. 받아쓰기형 문제로 확장 가능 |
| 모둠 협동 수비 모드 | 2단계 이후 | 6.3 참고 |
| 1·2단계 몬스터·문제 확장 | 파일럿 이후 | 16.3, 8.3 참고 |
